# Build environment — reproducing the port + its measurement

Everything needed to build the ported TUs and measure byte-exactness. Windows host; commands shown for the
Bash tool (git-bash). Paths are relative to the `bw1-dtk` worktree root unless noted.

## Toolchain facts

| Thing | Value / location | Why it matters |
|---|---|---|
| Compiler | **MSVC 6.0 SP5 = `cl.exe` `12.00.8804`**, under `build/compilers/MSVC/6.5/` | Identical to `bw1-decomp`'s staging compiler → verified bodies reproduce byte-exact |
| Target | **BW1E142** (`config/BW1E142/`) = our `win1.41` binary; sha1 of our rebuilt exe = `bccccbd3…` = dtk's `orig/BW1E142/runblack-decrypted.exe` | The objdiff *target* is the real original, split from the exe by `dtk pe split` |
| Build driver | `ninja` — **use the long-path-aware pip ninja `1.13`** at `<workspace>\.venv\Scripts\ninja.exe` | **NOT** Strawberry Perl's ninja — see MAX_PATH below |
| objdiff | `build/tools/objdiff-cli.exe` | `report` for match %, `diff` for per-instruction (see below) |

## The MAX_PATH gotcha (Windows)

Some STL-template `.o` names exceed 260 characters. Strawberry's ninja can't `Stat()` them
(`Filename longer than 260 characters`) and the build dies. The **pip ninja 1.13** (kitware build) is
long-path-aware and works. `LongPathsEnabled=1` is already set in the registry. Renaming the long symbols
does **not** help — `dtk pe split` regenerates `symbols.txt` on every configure.

## Header environment

The dtk source needs `bw1-decomp`'s headers. They are **git-ignored** and regenerated by:

```bash
tools/port_setup.sh        # seeds include/ from ../bw1-decomp: black/ (flat headers),
                           # libs/ (lionhead, chlasm, ...), and the stdlib_compat shims
```

`configure.py`'s `cflags_base` was extended to find them plus the CRT:

```
/I include  /I include/black  /I build/compilers/MSVC/6.5/include
```

One source fix lives in `bw1-decomp` itself: **`LH_RETURN`** is defined in BOTH
`libs/lionhead/lhlib/ver5.0/LHScript.h` and `libs/lionhead/lhmultiplayer/ver4.0/LHTransportInfo.h`. A TU
that pulls both (dtk's large combined TUs do) double-defines it. Both copies are guarded with
`#ifndef BW1_LH_RETURN_DEFINED`.

## config.yml — modules removed

The four DLL modules (`LHAudio`, etc.) are commented out of `config/BW1E142/config.yml`: we don't have the
v1.42 DLLs, so a full **link** fails. We don't link — **per-object objdiff** needs no link. All measurement
is per-`.o`.

## Building + measuring

Compile the ported objects (reconfigure happens automatically when `splits.txt`/`configure.py` change):

```bash
NJ=".../.venv/Scripts/ninja.exe"
TARGETS=$(for f in src/Black/Bank_*.cpp src/Black/Abode.cpp src/Black/Villager_*.cpp \
                   src/Black/GGame_*.cpp src/Black/SpellIcon_*.cpp \
                   src/Black/GameThingWithPos_*.cpp src/Black/AsmBank_*.cpp; do
            echo build/BW1E142/$f; done | sed 's|\.cpp$|.o|')
"$NJ" -k 0 $TARGETS          # -k 0 = keep going so one bad TU doesn't stop the rest
```

Generate the match report and count byte-exact functions:

```bash
build/tools/objdiff-cli.exe report generate -p . -o rep.json
# fuzzy_match_percent == 100  <=>  byte-exact
python3 -c "import json; d=json.load(open('rep.json')); \
  print(sum(1 for u in d['units'] if '/Black/' in (u['name'] or '') \
        for f in u['functions'] if (f.get('fuzzy_match_percent') or 0)>=100))"
```

## The per-instruction diff method (for near-misses)

`objdiff-cli report` only gives percentages. To see *why* a function differs, use `diff` with the symbol —
the structure was the gotcha: instructions live under **top-level `left.symbols[]` / `right.symbols[]`**,
NOT nested in sections.

```bash
objdiff-cli.exe diff -1 build/BW1E142/obj/Black/<TU>.o \
                     -2 build/BW1E142/src/Black/<TU>.o \
                     "?Mangled@Class@@..." -o sym.json --format json
# left = target (original), right = ours; each symbol has instructions[i].instruction.formatted
python3 -c "import json,itertools; d=json.load(open('sym.json')); S='?Mangled@Class@@...'; \
  g=lambda side:[ (i.get('instruction') or i)['formatted'] \
    for s in d[side]['symbols'] if s['name']==S for i in s['instructions'] ]; \
  [print('%-32s%s %s'%(l,'  ' if l==r else '<<',r)) \
    for l,r in itertools.zip_longest(g('left'),g('right'),fillvalue='')]"
```

Note: objdiff *normalizes* relative-jump offsets and reloc targets, so `je short 0xNN` vs `je short 0xMM`
and `[0xADDR]` vs `[__real@...]` are matches even though the formatted text differs — ignore those when
eyeballing; the real diffs are reordered/changed instructions.
