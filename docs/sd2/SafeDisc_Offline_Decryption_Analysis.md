# SafeDisc offline decryption — feasibility

Why v1.10 has a recoverable static key and v1.20 does not, and why a v1.20 offline
keystream regenerator is redundant.

v1.10 has a true static key (recovered and shipped in `tools/sd2decrypt`). v1.20 does not:
its keystream is generated by a stateful, plaintext-dependent (CFB) machine whose seed is
derived at runtime. A v1.20 offline regenerator is fully mapped and buildable but reproduces
output already obtained by dumping the running game once.

---

## The two protections are different ciphers

| | v1.10 (SafeDisc 2.30.033) | v1.20 (SafeDisc 2.60.052) |
|---|---|---|
| `.text` cipher | SDS-BPT + TEA-32 (keyed block cipher) | SDS-BPT + byte-wise AES-CFB (stateful stream) |
| The "key" | 16 bytes, static | a stateful C++ key-machine |
| Keystream | fixed given the key | plaintext-dependent (CFB feedback) |
| Per-byte key material | one TEA key | regenerated every byte by a C++ object graph |
| Portable / reusable? | yes | no — it is the runtime state |
| Decrypt any copy offline from the key? | yes | no — must run it to obtain the state |

v1.10 key (in `tools/sd2decrypt`): `40628063 c34bb1d8 f53b77f8 31ff40a0`.
`SDS-BPT + TEA(key)` reproduces the runtime decryption 100%.

## v1.20 has no static key — verified

- Self-consistent AES-256 schedule scan (`_src/aes_keyscan.py`, full FIPS-197 expansion
  present in memory) over both the mid-bulk dump and the OEP dump: 0 keys found.
  (`expand256` validated against FIPS-197 A.3: `w8 = 9ba35411`.)
- Direct byte search for the candidate noted during analysis (`1d19914e…`): absent (not even
  the first 8 bytes) in the final dumps. It was a transient/mislabeled value, not a usable key.

The cause is structural (see `SafeDisc_Cipher.md`): v1.20's `.text` cipher regenerates its
per-stage key material (`0x20/0x18/0x10` bytes) every byte via a C++ object graph, and the
keystream depends on the plaintext it just produced (CFB). There is no fixed 16/32-byte value
to lift, and no static key reproduces the keystream.

## Why the offline regenerator is redundant

The only reason to build an offline keystream regenerator is to decrypt without running the
protected exe. For v1.20:

1. Building and verifying the regenerator requires the runtime state (the dump) as ground truth.
2. Once the dump exists, the decryption is already in hand — that is `SD2cleaned.exe`.

So the regenerator is circular: substantial reverse-and-reimplement work to reproduce what a
dumper produces in one run. The structure is fully mapped; the cost/benefit is what makes it
not worth building.

The one theoretical exception is an exe that genuinely cannot be run anywhere. But v1.20's
keystream is CFB (plaintext-fed) and seeded by runtime-derived material, so the seed state must
still be recovered by running it once — at which point the image can be dumped.

## How SafeDisc 2.x is defeated here

By unpacking, not by reimplementing the cipher:

```
run the game once  ->  loader decrypts .text in memory + resolves imports
  ->  dump the decrypted image at the OEP        (SD2_UNPACK / SD2cleaned.exe)
  ->  reconstruct the import table               (imptrace.py -> rebuild_nocd.py)
  ->  set EntryPoint = OEP, neuter the loader     (runblack_nocd.exe)
```

Result: `runblack_nocd.exe` loads with no disc and no SafeDisc and reaches the original game
entry point (`OEP 0x7ca49f`), validated by debug-launch to the OEP with all imports resolved.

## Summary

- v1.10: a static key exists; recover it → offline decryptor (`tools/sd2decrypt`).
- v1.20: no static key. The deliverables are the unpacked image (`runblack_nocd.exe`) and the
  cipher RE in `SafeDisc_Cipher.md`. An offline regenerator is specified but redundant.
